# 上海大学科学家精神数字展馆 V1 质量审计与更新设计

**日期：** 2026-08-27  
**状态：** 待用户书面审阅  
**目标：** 先发布已完成的 V1 终审加固，再在不改变既定视觉方向的前提下，对代码、视觉、内容、逻辑和页面进行证据驱动的全面审计与更新。

## 1. 背景与边界

V1 已合入 `main` 并通过 GitHub Pages 上线，但此前终审通过的一批加固修改仍保存在 `feat/museum-v1` 工作树中，尚未提交。项目同时需要一次覆盖全站的质量回顾，以发现上线后仍可能存在的视觉、内容、逻辑、页面和代码问题。

本轮保持“红色文化 × 科技档案 × 现代博物馆”的既定定位、信息架构和核心视觉语言。允许修正布局层级、间距、对比度、响应式、动效和可访问性问题，不进行整体改版，不新增与审计无关的功能。

## 2. 执行策略

采用两阶段、两次发布，避免把已经复审的加固改动与开放式审计混在同一批次。

### 阶段一：终审加固发布

1. 在现有 `feat/museum-v1` 工作树中，从当前状态创建 `fix/v1-hardening`。
2. 提交此前已经实现并复审通过的加固修改，包括：
   - Pages 部署执行完整质量门禁并收紧权限；
   - Open Graph 图片适配部署 base；
   - 媒体外链仅允许有效 HTTPS 地址；
   - 加强 CountUp、首页统计、三种部署 base 的回归测试；
   - 删除内部过程报告并清理公开文档中的本机绝对路径。
3. 运行完整本地门禁和端到端测试。
4. 推送修复分支，合入 `main`，等待 CI 与 Pages 部署成功。
5. 验证线上首页、人物深链、图片、Open Graph 资源和移动端导航。

阶段一不接受额外功能或视觉修改。若验证发现阶段一代码自身缺陷，仅修复该缺陷后再发布。

### 阶段二：全站质量审计与更新

1. 从阶段一发布后的 `main` 创建 `audit/v1-quality-round-1`。
2. 建立可复现的审计基线和问题清单。
3. 按代码、视觉、内容、逻辑、页面五个维度审计。
4. 只修复有证据的问题；每个修复先形成失败证据或明确的视觉/内容对照证据。
5. 每个独立修复任务单独提交并经过独立复审。
6. 全分支终审、完整验证后合入 `main`，完成第二次发布与线上验收。

## 3. 审计维度

### 3.1 代码

- 查找重复实现、无效分支、未使用导出、过期配置和不必要依赖。
- 检查组件职责、类型边界、错误处理、资源路径和部署配置。
- 删除代码前必须证明无引用、无运行时依赖，并由测试保护相关行为。
- 不以“代码更漂亮”为理由进行大规模重构；重构必须直接服务于已确认的问题。

### 3.2 视觉

- 保留现有配色、字体体系、档案感、卡片语言和内容结构。
- 在 360、390、768、1024、1440 像素宽度检查横向溢出、文字截断、图片比例、间距、层级、焦点、对比度和触控尺寸。
- 检查普通动效与 `prefers-reduced-motion` 降级。
- 修复标准是清晰、一致、可访问、跨设备稳定，而不是主观换风格。

### 3.3 内容

- 审核人物姓名、年份、机构、成果、奖项、事件、图片说明和页面标题。
- 新增或修改事实必须登记可追溯来源。
- 来源优先级：
  1. 上海大学及其院系、档案馆等官方来源；
  2. 正式发表的论文、学术数据库记录和出版社资料；
  3. 国家级机构、主流正式媒体或权威人物纪念资料。
- 关键事实尽量交叉验证；搜索摘要、百科、自媒体不能作为最终依据。
- 找不到可靠依据时保留“待收集”，不推测、不造图、不虚构活动或成果。
- 有可靠来源时补全明显空缺和占位内容，但不为增加篇幅而堆砌材料。

### 3.4 逻辑

- 检查路由、深链刷新、404 恢复、GitHub Pages base 和资源 base。
- 检查筛选 URL、浏览器前进后退、状态恢复和空结果重置。
- 检查移动导航、弹窗焦点、Escape、图谱列表降级、图片失败降级和外链安全。
- 检查 `planned`、`collecting`、`published` 等内容状态与页面动作是否一致。
- 逻辑缺陷必须先由测试或最小复现证明，再修改实现。

### 3.5 页面

逐页检查：

- 首页；
- 前辈群像；
- 钱伟长、李三立、黄宏嘉人物专题；
- 岁月长河；
- 精神谱系；
- 科学家图谱；
- 精神足迹；
- 影音档案；
- 关于项目；
- 404 页面。

每页检查导航可达性、标题层级、正文可读性、图片与替代文本、链接、加载失败状态、控制台错误、键盘操作、移动端布局和深链刷新。

## 4. 证据与修复规则

- 代码和逻辑问题：使用自动化测试形成 RED，再做最小 GREEN。
- 视觉问题：保留修复前后相同视口截图，并将可自动化的溢出、焦点、可见性问题写入 E2E。
- 内容问题：记录原文、修改内容、来源 URL、来源类型和核验日期。
- 资料存在冲突时，以更直接、更权威、更接近原始记录的来源为准；无法裁定则不修改事实并记录争议。
- 不修改用户资料库原件，不把本机路径、缓存、构建产物或内部过程报告提交到公开仓库。

## 5. 验证与发布门禁

每个发布候选必须通过：

1. `npm ci`；
2. 内容校验；
3. ESLint；
4. TypeScript 类型检查；
5. 全部 Vitest；
6. 生产构建；
7. 现有 16 项 Playwright E2E，以及本轮新增回归用例；
8. 360、390、768、1024、1440 五档响应式检查；
9. PC 与移动端逐页视觉验收；
10. GitHub CI 与 Pages 部署成功；
11. 线上深链、图片、内部链接、外链、控制台和资源请求验收。

若标准命令受执行环境权限限制，必须记录限制并在拥有正常文件权限的环境重新运行原始命令；替代 runner 只能提供诊断证据，不能替代最终发布门禁。

## 6. 交付物

- 阶段一修复提交、合并记录和线上验收结果；
- 阶段二审计分支及按问题拆分的修复提交；
- 内容来源登记和必要的内容指南更新；
- 视觉对照证据与新增自动化测试；
- 最终审计报告，按“已修复、保留、仍需团队补充”分类；
- 更新后的公开 V1 站点。

## 7. 明确不做

- 不改变网站核心定位、主色、整体叙事顺序或主要页面集合；
- 不新增后台、数据库、登录、评论或内容管理系统；
- 不用生成图替代缺少的历史档案；
- 不发布无法核实的活动、影音链接或人物成果；
- 不在本轮进行与问题无关的大规模技术栈升级。
